1.1. DESBALANCEO DE CLASES
--------------------------------------------------------------------------------

PROBLEMA:
La clase B+ representa solo 1.35% del dataset (676 muestras de 50,000), 
mientras que A- representa 49.60% (24,798 muestras). Esta disparidad 
resulta en:

- F1-Score de B+ = 0.6695 (el más bajo)
- Modelo tiende a predecir clases mayoritarias
- 39 falsos positivos de B+ como B1

IMPACTO EN RESULTADOS:
┌────────┬──────────┬───────────┬──────────────────┐
│ Clase  │ % Datos  │ F1-Score  │ Impacto          │
├────────┼──────────┼───────────┼──────────────────┤
│ A- (0) │  49.60%  │  0.9489   │ Excelente        │
│ A1 (1) │  28.29%  │  0.8849   │ Muy bueno        │
│ A2 (2) │  14.44%  │  0.9400   │ Excelente        │
│ B+ (3) │   1.35%  │  0.6695   │ Limitado ⚠       │
│ B1 (4) │   6.32%  │  0.9565   │ Excelente        │
└────────┴──────────┴───────────┴──────────────────┘

SOLUCIONES POTENCIALES:
1. Class Weighting: Asignar peso mayor a clases minoritarias en loss
   - w_i = n_samples / (n_classes × n_samples_class_i)
   - Loss_weighted = Σ w_i × loss_i

2. SMOTE (Synthetic Minority Over-sampling):
   - Generar muestras sintéticas de B+ mediante interpolación
   - K-NN para identificar vecinos cercanos
   - Crear muestras entre punto original y vecinos

3. Focal Loss:
   - FL(p_t) = -(1 - p_t)^γ × log(p_t)
   - Reduce peso de ejemplos bien clasificados
   - Enfoca aprendizaje en ejemplos difíciles

4. Ensemble con Modelos Especializados:
   - Un modelo para distinguir mayoría vs minoría
   - Otro modelo especializado en clases minoritarias


1.2. SENSIBILIDAD A HIPERPARÁMETROS
--------------------------------------------------------------------------------

HIPERPARÁMETROS CRÍTICOS:

Learning Rate:
- Muy alto: Divergencia (loss explota)
- Muy bajo: Convergencia lenta (requiere muchas epochs)
- Valor usado: 0.01 con decay 0.98 (funcionó bien)

Arquitectura (neuronas por capa):
- Muy pocas: Underfitting (no captura complejidad)
- Muchas: Overfitting (memoriza training data)
- Valor usado: 10→20→10→5 (balance adecuado)

Batch Size:
- Muy pequeño: Gradientes ruidosos, entrenamiento inestable
- Muy grande: Convergencia a mínimos sharp, menos generalización
- Valor usado: 64 (buen balance)

EVIDENCIA DE SENSIBILIDAD:
Sin optimización de hiperparámetros, el modelo podría rendir:
- Caso pesimista: Accuracy 75-80% (hiperparámetros muy malos)
- Caso actual: Accuracy 92.66% (hiperparámetros razonables)
- Caso óptimo: Accuracy 93-95% (hiperparámetros finamente ajustados)

SOLUCIÓN: Grid Search o Random Search con validación cruzada


1.3. RIESGO DE MÍNIMOS LOCALES
--------------------------------------------------------------------------------

NATURALEZA DEL PROBLEMA:
La función de loss es no convexa con múltiples mínimos locales.
SGD puede quedar atrapado en óptimos subóptimos.

EVIDENCIA EN NUESTRO CASO:
- Convergencia a val_loss = 0.2004 (¿es el mínimo global?)
- No tenemos garantía de que sea el mejor resultado posible

MITIGACIONES APLICADAS:
✓ Momentum (0.9): Ayuda a escapar mínimos locales poco profundos
✓ Learning rate decay: Permite exploración inicial y refinamiento final
✓ Inicialización He/Xavier: Punto de partida razonable

SOLUCIONES ADICIONALES:
1. Múltiples Inicializaciones Aleatorias:
   - Entrenar 5-10 modelos con diferentes seeds
   - Seleccionar el mejor en validation
   - Ensemble de los top 3

2. Optimizadores Adaptativos:
   - Adam: learning rates adaptativos por parámetro
   - RMSprop: similar pero sin momentum
   - Mejor convergencia en muchos casos

3. Learning Rate Scheduling Avanzado:
   - Cosine Annealing: lr oscila siguiendo coseno
   - Cyclical LR: aumenta y disminuye periódicamente
   - Warm Restarts: resetea lr periódicamente


1.4. INTERPRETABILIDAD LIMITADA
--------------------------------------------------------------------------------

PROBLEMA:
A diferencia de árboles de decisión o regresión logística, MLP es una "caja negra":
- Difícil explicar por qué se tomó una decisión específica
- Pesos no tienen interpretación directa intuitiva
- 450 parámetros interactuando de forma no lineal

IMPACTO:
- En aplicaciones críticas (medicina, justicia): falta de confianza
- Difícil detectar sesgos en el modelo
- Complicado para stakeholders no técnicos

SOLUCIONES:
1. Feature Importance por Perturbación:
   - Modificar cada feature y medir impacto en predicción
   - Ranking de importancia relativa

2. LIME (Local Interpretable Model-agnostic Explanations):
   - Aproximación local con modelo lineal interpretable
   - Explica predicciones individuales

3. SHAP (SHapley Additive exPlanations):
   - Valores de Shapley de teoría de juegos
   - Contribución justa de cada feature

4. Visualización de Activaciones:
   - Analizar qué patrones activan neuronas específicas
   - Entender jerarquía de representaciones


1.5. CAPACIDAD LIMITADA SIN TÉCNICAS AVANZADAS
--------------------------------------------------------------------------------

TÉCNICAS NO IMPLEMENTADAS:

Regularización Adicional:
- Dropout: Desactivación aleatoria de neuronas (previene co-adaptación)
- Batch Normalization: Normaliza activaciones (acelera entrenamiento)
- Data Augmentation: Aumenta diversidad de datos

Optimizaciones de Arquitectura:
- Skip Connections (ResNet): Facilita entrenamiento de redes profundas
- Attention Mechanisms: Enfoca en partes relevantes de input
- Multi-task Learning: Aprende representaciones compartidas

IMPACTO DE SU AUSENCIA:
- Dropout: Posible overfitting en capas ocultas
- Batch Norm: Convergencia potencialmente más lenta
- Data Aug: Menor robustez a variaciones de datos

JUSTIFICACIÓN DE NO IMPLEMENTACIÓN:
✓ Complejidad adicional significativa (100-300 LOC cada una)
✓ Objetivo educativo ya cumplido con implementación base
✓ Resultados actuales ya son competitivos

2.2. SIN PARALELIZACIÓN
--------------------------------------------------------------------------------

OPORTUNIDADES DE PARALELIZACIÓN:

1. Operaciones de Matriz-Vector:
   - Forward pass: cada neurona independiente
   - Backward pass: cálculo de gradientes paralelo
   - Speedup teórico: 2-4x en CPUs multi-core

2. Mini-batch Processing:
   - Procesar múltiples muestras simultáneamente
   - GPU sería ideal pero OpenMP en CPU también ayuda

IMPLEMENTACIÓN CON OpenMP:
```c
#pragma omp parallel for
for (int i = 0; i < layer->num_neurons; i++) {
    layer->pre_activation[i] = layer->biases[i];
    for (int j = 0; j < layer->num_inputs; j++) {
        layer->pre_activation[i] += layer->weights[i][j] * input[j];
    }
}
```

BENEFICIOS ESPERADOS:
- CPU 4-core: 2.5-3x speedup
- CPU 8-core: 4-5x speedup
- Tiempo de 1.57s → ~0.4-0.6s

CONSIDERACIONES:
- Overhead de threads para matrices pequeñas
- Memory contention si no se gestiona bien cache


2.3. SIN OPTIMIZADORES AVANZADOS
--------------------------------------------------------------------------------

IMPLEMENTADO:
✓ SGD (Stochastic Gradient Descent)
✓ Momentum

NO IMPLEMENTADO:
✗ Adam (Adaptive Moment Estimation)
✗ RMSprop
✗ AdaGrad
✗ Nadam (Adam + Nesterov momentum)

IMPACTO:
Adam típicamente converge más rápido y es más robusto:
- Menos sensible a learning rate
- Learning rates adaptativos por parámetro
- Mejor para datos sparse

COMPARACIÓN ESPERADA:
┌──────────────┬─────────────┬────────────────┐
│ Optimizer    │ Epochs      │ Val Accuracy   │
├──────────────┼─────────────┼────────────────┤
│ SGD          │ 31 (actual) │ 0.9223         │
│ SGD+Momentum │ Similar     │ Similar        │
│ Adam         │ ~20-25      │ ~0.925-0.930   │
└──────────────┴─────────────┴────────────────┘

IMPLEMENTACIÓN DE ADAM (pseudocódigo):
```c
// Mantener running averages de gradientes y gradientes^2
m = beta1 * m + (1 - beta1) * grad;
v = beta2 * v + (1 - beta2) * grad^2;

// Corrección de bias
m_hat = m / (1 - beta1^t);
v_hat = v / (1 - beta2^t);

// Actualización
weights -= learning_rate * m_hat / (sqrt(v_hat) + epsilon);
```


2.4. GESTIÓN MANUAL DE MEMORIA
--------------------------------------------------------------------------------

DESAFÍOS:

1. Riesgo de Memory Leaks:
   - Cada malloc() debe tener correspondiente free()
   - Estructuras anidadas requieren liberación cuidadosa
   - Errores pueden acumular memoria perdida

2. Complejidad de Debugging:
   - Valgrind para detectar leaks
   - Segmentation faults si se accede memoria no válida
   - Difícil rastrear origen de problemas

EVIDENCIA DE BUENA GESTIÓN EN NUESTRA IMPLEMENTACIÓN:
✓ Funciones free_dataset(), free_mlp(), free_metrics()
✓ Liberación en orden inverso a asignación
✓ Validación de malloc() != NULL

VERIFICACIÓN CON VALGRIND (recomendado):

5.3. BALANCE ENTRE SIMPLICIDAD Y CAPACIDAD
--------------------------------------------------------------------------------

FILOSOFÍA DE DISEÑO:
"Hacer el modelo MÁS SIMPLE que funcione bien"

TRADE-OFFS ACEPTADOS:
- Menos features → Código más comprensible
- Menos optimizadores → Implementación más clara
- Arquitectura fija → Menos complejidad de parsing

BENEFICIO:
✓ Código legible y mantenible
✓ Fácil de entender para propósitos educativos
✓ Base sólida para extensiones futuras


5.4. LECCIONES APRENDIDAS
--------------------------------------------------------------------------------

1. SIMPLICIDAD FUNCIONA:
   - No se necesitan 100 features para 92% accuracy
   - SGD + Momentum es suficiente para convergencia
   - Arquitectura simple (2 capas ocultas) es efectiva

2. OPTIMIZACIÓN IMPORTA:
   - Flags de compilación (-O3): 2-3x speedup
   - Inicialización correcta: Evita horas de debugging
   - Early stopping: Previene overfitting automáticamente

3. VALIDACIÓN ES ESENCIAL:
   - Comparar con baselines conocidos
   - Verificar con múltiples métricas
   - Análisis de errores por clase

4. DOCUMENTACIÓN VALE ORO:
   - Código auto-documentado facilita mantenimiento
   - Diagramas y pseudocódigo aceleran comprensión
   - Comentarios en decisiones no obvias
